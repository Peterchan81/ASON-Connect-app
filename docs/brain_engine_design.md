# ASON Connect V2 — Brain Engine 설계 문서

> 상태: **설계안 (구현 전, 승인 대기)**
> 이 문서는 코드가 아닙니다. 승인 후 이 설계를 기준으로 구현을 진행합니다.

---

## 0. 설계 원칙

Brain Engine을 만들 때 지키는 원칙은 다음 세 가지입니다.

1. **입력 폼이 아니다.** 값이 빠졌다고 "시간은?", "장소는?"처럼 하나씩 되묻지 않는다. 이해한 만큼 곧바로 결과 카드를 만들고, 나머지는 사용자가 수정으로 채운다.
2. **거짓으로 채우지 않는다.** 추출하지 못한 필드는 비워 둔다. 추측으로 지어내지 않는다.
3. **Core와 같은 저장 구조를 그대로 쓴다.** Connect는 별도의 저장소를 새로 만들지 않고, ASON Core가 이미 쓰는 저장 키/형태를 그대로 따른다.

## 1. 전체 처리 흐름

```
사용자 입력(음성/문자)
        │
        ▼
┌───────────────────┐
│   Brain Engine     │
├───────────────────┤
│ ① 의도 분석         │  문장 안에 있는 의도 신호를 스캔한다
│ ② 의도 분리         │  신호 경계를 기준으로 문장을 절(clause)로 나눈다
│ ③ 필드 추출         │  절마다 날짜/시간/장소/내용/알림/반복을 뽑는다
│ ④ 부족 정보 판단     │  "질문이 필요한가"를 판단한다 (대부분 아니오)
│ ⑤ 결과 카드 생성     │  절마다 하나의 결과 카드(DraftCommand)를 만든다
└───────────────────┘
        │
        ▼
   사용자 확인 / 수정
        │
        ▼
   ASON Core 동기화
        │
        ▼
       완료
```

**핵심 순서 원칙**: ①→②를 먼저 하고 나서 ③을 하는 이유는, 절을 먼저 정확히 나눠야
③ 필드 추출 단계에서 "다른 절의 내용"이 지금 절의 내용/알림 필드로 섞여 들어가는
사고를 막을 수 있기 때문입니다. (예: "…스트레칭하기"가 일정의 알림 필드에 섞이는 사고)

절이 하나뿐인 입력(가장 흔한 경우)은 ②에서 그대로 통과하고, ③~⑤가 한 번만 실행됩니다.

## 2. 의도 분석 구조

### 2.1 분류 대상 (정확히 4종류)

| 종류 | 핵심 신호 |
|---|---|
| 일정 | 날짜/시간 표현, 미팅·회의·약속·병원·방문 등의 단어, 장소 표현 |
| 나의 하루 목표 | 반복 표현("매일/매주/매달") + 행동 단어(운동/스트레칭/공부/물 마시기 등) |
| 다이어리 | 과거형 감정 표현("좋았다/힘들었다/즐거웠다" 등), "기분"/"일기" 단어 |
| 메모 | 기억/기록/구매 표현, 날짜·반복 신호가 전혀 없는 한 번뿐인 할 일("~하기"로 끝나는 문장) |

> 내부적으로는 기존에 있던 건강/프로젝트/할 일 분류기가 계속 남아 함께 채점됩니다
> (하위 호환용). 사용자에게는 이 4종류만 노출됩니다. 새 문장이 건강/프로젝트로
> 강하게 분류되면(예: "오늘 혈압 128에 82") 그 결과를 그대로 쓰고, 애매하면 4종류
> 쪽으로 기울도록 신호를 설계합니다.

### 2.2 채점 방식

카테고리마다 **점수 = 키워드 일치 개수 + 구조적 신호 보너스**로 계산합니다.

- 키워드 일치: 카테고리별 사전에 있는 단어가 문장에 있으면 +1씩 (최대 +2)
- 구조적 신호 보너스 (더 강한 증거이므로 키워드보다 크게):
  - 일정: 시간 표현 있음 +2, 확실한 장소 있음 +2
  - 나의 하루 목표: 반복 표현("매일/매주/매달") 있음 +3
  - 다이어리: 과거형 감정 표현 있음 +3
  - 메모: 구매/기억 표현 +2, 반복 표현 없이 "~하기"로 끝나는 문장 +2

### 2.3 판정

- **미분류**: 모든 카테고리 점수 0점 → 카드를 만들지 않고, 자연스러운 일반 대화
  응답만 돌려준다. (예: "오늘 피곤해" → 되묻지 않고 짧게 반응)
- **애매**: 1·2위 점수가 가깝고(차이 ≤ 1) 1위 점수도 낮을 때(< 3점) → **딱 한 번**
  "A로 정리할까요, B로 정리할까요?"라고 묻는다. 이건 "필드가 부족해서 묻는 질문"이
  아니라 "종류 자체가 안 정해져서 묻는 질문"이라 원칙 1과 충돌하지 않는다.
- **분류됨**: 그 외 → 해당 카테고리로 확정하고 필드 추출로 넘어간다.

## 3. 다중 의도 처리

한 문장에 여러 의도가 섞여 있을 수 있습니다. 예:
"내일 오후 3시 광고미팅하고 한 시간 전에 알려주고 매일 아침 스트레칭하기."
→ (일정: 광고미팅) + (나의 하루 목표: 스트레칭)

### 3.1 절 나누기 순서

1. **구분자 분리**: 쉼표, 마침표, 느낌표로 먼저 나눈다.
2. **구분자가 없을 때(가장 흔한 실제 입력 형태)**: 입력창은 한 줄 텍스트라 사용자가
   쉼표 없이 이어 말하는 경우가 많다. 이때는 "매일/매주/매달" 같은 반복 신호가
   문장 중간에 나타나는 지점을 경계로 앞/뒤 두 절로 나눈다. (반복 신호는 나의 하루
   목표를 시작하는 가장 강한 신호이기 때문에 경계로 쓰기에 안전하다)
3. **되붙이기(병합)**: "한 시간 전에 알려주고"처럼 숫자+시간/분+"전"+알림 동사만
   있는 절은 새 항목으로 만들지 않고, 바로 앞 절에 이어붙인다. (앞 절의 알림
   필드가 되기 때문)

### 3.2 절 이후 처리

나뉜 절 하나하나를 §2(의도 분석)로 **독립적으로** 다시 판단합니다. 절이 여러 개면
결과 카드도 그 수만큼 생깁니다.

## 4. 필드 추출

### 4.1 일정

**추출 순서: 날짜 → 시간 → 장소 → 알림 → 반복 → (나머지 = 내용)**

문장에서 앞의 다섯 항목을 순서대로 "찾아서 제거"해 나가고, **마지막까지 남은
텍스트가 내용(제목)**이 됩니다. 이 "소거법" 방식이 핵심 설계입니다 — 내용을 먼저
추측하지 않고, 다른 모든 항목을 확실히 걷어낸 나머지만 내용으로 인정하기 때문에
"광고미팅 알람 1시간 전 반복 없음"처럼 통째로 삼키는 사고가 생기지 않습니다.

| 순서 | 항목 | 판단 방법 |
|---|---|---|
| 1 | 날짜 | "오늘/내일/모레/어제" 사전 + "n월 n일" 패턴 |
| 2 | 시간 | "(오전\|오후) n시 (n분)" 패턴. 오전/오후 없이 숫자만 있으면 업무 미팅 관행상 오후로 간주 |
| 3 | 장소 | 지역명 사전 + 행정구역/장소 접미사 패턴(단, "정리"처럼 흔한 일반 단어와 겹치는 접미사는 최소 글자수 조건을 둬 오탐을 막는다) |
| 4 | 알림 | "(숫자\|한/두/세…) (시간\|분) 전" + 주변의 "알람/알림/알려줘" 표현까지 함께 제거 |
| 5 | 반복 | "반복 없음/없이" 또는 "매일/매주 n요일/매달" |
| 6 | 내용 | 위 다섯 개를 걷어내고 남은 텍스트. 문장 연결 어미("~하고")와 존재 표현("~있어")만
       붙어 있으면 그것도 마저 걷어낸다. 남은 게 분류 키워드 한 단어뿐이면("미팅"만
       남는 경우) 실질적인 내용이 없는 것으로 보고 비워 둔다 |

### 4.2 나의 하루 목표

**추출 순서: 반복 → (나머지 = 내용)**

반복 표현("매일 아침" 등)을 먼저 찾아 떼어내고, 남은 텍스트에서 "~하기/~하자"
같은 문장 종결 어미를 정리하면 내용이 됩니다. (예: "매일 아침 스트레칭하기" →
반복="매일 아침", 내용="스트레칭")

### 4.3 다이어리

절 전체를 가볍게 다듬어(앞뒤 공백/문장부호 정리) 그대로 내용으로 씁니다. 감정을
표현한 문장 자체가 기록의 본질이라 별도로 필드를 쪼개지 않습니다.

### 4.4 메모

절 전체를 자연스러운 표현으로 다듬어(예: "~하고"→"~와", "~사야 해"→"구매") 내용으로
씁니다.

## 5. 부족 정보 판단

### 5.1 원칙: 질문 없이 결과 카드부터

Brain Engine은 **어떤 카테고리에서도 필드가 빠졌다는 이유로 되묻지 않습니다.**
지금까지 이해한 내용만으로 곧바로 결과 카드(준비 완료 상태)를 만들고, 빈 항목은
카드에 빈 채로 보여줍니다. 사용자는 수정 버튼으로 직접 채우거나, 빈 채로 그대로
동기화할 수 있습니다.

### 5.2 유일한 예외: 종류 자체가 불확실할 때

§2.3의 "애매" 판정을 받은 경우에만, 필드가 아니라 **카테고리 자체**를 묻는 질문을
한 번 합니다. ("일정으로 정리할까요, 메모로 정리할까요?") 이건 필드 수집 질문이
아니라 분류 확인 질문이라 원칙과 충돌하지 않습니다. 사용자가 답하면 그 즉시
카테고리가 확정되고 다시 묻지 않습니다.

### 5.3 이미 답한 정보는 다시 묻지 않는다

애초에 되묻는 경우가 §5.2 하나뿐이므로, "이미 말한 정보를 또 묻는" 상황 자체가
구조적으로 생기지 않습니다.

## 6. ASON Core 저장 구조

Connect는 새 저장소를 만들지 않고, ASON Core가 이미 쓰는 저장 키·데이터 형태를
**그대로** 따라 씁니다. (두 앱은 별도 프로세스라 서로 직접 호출할 수 없지만, 같은
기기에서 같은 로컬 저장 구조를 공유하면 나중에 한 저장소를 함께 읽고 쓸 수 있습니다)

| 의도 | Core 저장소 키 | 데이터 형태 |
|---|---|---|
| 일정 | `scheduleByDate` | 날짜별 JSON 배열 (id/시간/내용/완료여부/메모/알림여부) |
| 나의 하루 목표 | `todayGoals` | 오늘의 목표 JSON 배열 (id/내용/완료여부) |
| 다이어리 | `diaryEntries` | 날짜별 한 줄 기록 Map (날짜 → 문자열, 같은 날 여러 번이면 줄바꿈으로 이어붙임) |
| 메모 | `memoStoreV1` | JSON 배열 (id/제목/내용/종류/태그 등) |

건강/프로젝트(하위 호환 전용 내부 분류)는 각각 기존 건강/프로젝트 저장소를 그대로
사용합니다.

## 7. 동기화 순서

```
입력 (음성/문자)
   │
   ▼
분석 (자동, 무질문 — §5 원칙)
   │
   ▼
확인 (결과 카드로 표시)
   │
   ▼
수정 (선택 — 사용자가 원할 때만)
   │
   ▼
저장 (ASON Core 저장소에 upsert)
   │
   ▼
완료 ("ASON에 저장되었습니다" 안내 후 카드/입력창 초기화)
```

- 저장 시 id는 이 항목을 처음 만든 시각 기준으로 정해져, **같은 항목을 수정 후
  다시 저장해도 새로 생기지 않고 덮어씁니다.**
- 일정은 추가로 "날짜·시간·내용이 완전히 같은 다른 항목"이 이미 있는지 확인해,
  있으면 저장을 막고 중복으로 안내합니다. (§8.4)
- 다이어리는 하루에 여러 번 기록할 수 있으므로 upsert 대신 이어붙이기로 저장합니다.
- 여러 항목이 동시에 준비되면(다중 의도) 카드마다 개별 동기화 버튼과, 모두
  준비됐을 때 "모두 ASON에 동기화" 버튼을 함께 제공합니다.

## 8. 예외 처리

| 상황 | 처리 방식 |
|---|---|
| 분석 실패 (예상치 못한 오류) | "요청을 처리하지 못했습니다. 다시 말씀해 주세요." 안내만 하고, 지금 카드 상태는 그대로 유지 (앱이 죽지 않음) |
| 의도 불명확 (완전 미분류) | 카드를 만들지 않고, 자연스러운 짧은 응답만 돌려준다. 다시 말하도록 유도하되 강요하지 않는다 |
| 의도 애매 (두 후보 근접) | §5.2의 단발성 선택 질문 한 번만 |
| 중복 일정 | 저장을 거부하고 "이미 동일한 일정이 있습니다" 표시, 카드는 그대로 남아 재시도/수정 가능 |
| 저장 실패 (그 외 오류) | 실패 이유를 카드에 표시, 카드는 그대로 남아 재시도 가능 |

## 승인 요청

이 설계로 구현을 진행해도 되는지 확인 부탁드립니다. 특히 아래 두 가지는 이번
설계에서 새로 명확히 한 부분이라 확인이 필요합니다.

1. **§5** — 필드 부족 시 질문을 완전히 없애고, 카테고리 자체가 애매할 때만
   예외적으로 한 번 묻는 것으로 확정해도 되는지
2. **§2.1** — 건강/프로젝트/할 일은 사용자에게 노출하지 않는 내부 하위 호환
   분류로만 남기고, 사용자 대상 결과는 4종류(일정/나의 하루 목표/다이어리/메모)로
   한정하는 방향이 맞는지

승인해 주시면 이 문서를 기준으로 구현을 시작합니다.
